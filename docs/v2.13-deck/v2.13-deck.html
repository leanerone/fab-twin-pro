雷区 A · 根因

lot_id / alarm_code 埋在 payload_json CLOB 大文本里。数据库索引只能建在"列"上，建不了 CLOB 内部字段。Oracle 11g 也没有 JSON_VALUE 函数索引。

雷区 B · 根因

表上缺少 (tool_id, raw_id) 复合索引。翻页查询要 ORDER BY raw_id DESC，没索引就得临时排序 → 全表扫描。

问题口播：三个查询都要 500-600 秒，根因是查询条件在 CLOB 大文本里，索引建不上。

Feasibility · Fluent Bit 方案细化

同事方案（Fluent Bit → DB）优势 · 待确认点 · 与 v2.13 对比

✅ 已确认的优势（Fluent Bit 背书）

  • 机台性能无影响——Fluent Bit 用 inotify 文件监控，CPU < 1%、内存几十 MB，工业级已在大量晶圆厂部署；不会强机台（之前担心的 tail -f 方案已经淘汰）
  • log 已可获取上传——同事这边已有成熟的 log 采集链路，不是从 0 开始
  • 字段天然独立列——lot_id / recipe_id / chamber_id 在 log 里就是独立字段，写入时直接 INSERT 成列，等于 v2.13 的物化列在源头就解决了
  • 不需要 payload_json + 物化列 + 回填脚本——整条链路都省了
  • 写入路径更短——跳过 RV + 后端 API，每事件延迟 < 1s；RV 故障（总线抖动/断连）时 log 方案不受影响
  • 可补历史数据——旧 log 文件能回填任意时间段，RV 消息队列通常只保留最近 3–7 天

⚠️ 待确认点（非 blocker）

  • 多机台格式——AMAT / Applied Materials / 自研机台 log 正则不同，Fluent Bit 配置文件要多套；已可通过 regex parser + 多 tail 源解决（非技术难题，需盘点）
  • RV 合同兼容性——当前 RV 路径是已在生产稳定运行的合同方案，新方案不替代，并行部署；写入双轨期间两边数据一致性需确认
  • 语义对齐——log 字段映射到 DT_EVENT_RAW 各列的规则需和当前 RV payload_json 对齐（lot_id / alarm_code / event_name 命名一致）
  • 异常处理——正则解析失败的行要落 error 表并告警；Fluent Bit 本身支持 @ERROR 路由

  • 写入架构不动（继续 RV），查询侧根治
  • DDL 变更：加 3 列 + 4 索引 + 触发器
  • 历史回填 998 万行 ≈ 15 min
  • 今天就能部署，风险可控

同事 Fluent Bit 方案（建议 P2 立项）

  • 新表 schema 设计（字段直接拆列）

两套方案不冲突——v2.13 用最小改动解决当前紧急问题（现场查询 500 秒超时），Fluent Bit 是架构升级，让新写入的事件从源头就是好数据。后续 log 方案上线后，v2.13 的物化列 + 触发器仍可保留用于兼容过渡期数据。
可行性口播：同事用的 Fluent Bit 是工业级的，CPU<1% 不影响机台，log 已能拿到，所以可行性比之前判断高很多。两套方案不冲突——v2.13 快、log 方案彻底，建议并行推进。

What Changed

v2.13 改了什么

🗄️ 数据库侧（全部 ADD）

  • 加 3 列：LOT_ID / EVENT_NAME / ALARM_CODE（之前根本不存在）
  • 加 4 索引：LOT / ALARM / NAME + 补 (TOOL_ID, RAW_ID)
  • 加 1 触发器：TRG_DT_EVENT_RAW_EXTRACT，从 payload_json REGEXP_SUBSTR 提取三列
  • 不删不改任何已有列 / 数据 / payload_json 原文
  • DDL 幂等，可重复执行，DBA 工单已准备好

💻 应用侧

  • 14 处 LIKE 改等值（payload_json LIKE '%lot%' → LOT_ID = 'xxx'）
  • ORM before_insert listener 全覆盖写入点（rvmessages / simulator / ODS / debug）
  • 历史回填脚本（tests/backfill_event_columns.py）：998 万行 906s，支持断点续跑 + verify
  • 旧列不存在时代码自动降级回退（DBA 脚本未跑也不报错）
  • 本地 998 万行开发库全链路验证通过（commit 1143801）
改动口播：改了两类——DB 4 项 ADD 操作，应用 14 处改写。全部加操作，无删无改。

Deployment Plan · 在线 6 步

不停机，DBA 先跑脚本 → 起后端 → 低峰回填

①DBA 执行 sql/v2.13_add_event_extract_columns.sql（加列 + 索引 + 触发器）
②git pull origin/test3 + 重启后端进程
③DBA + 开发验证 USER_TAB_COLUMNS / USER_INDEXES / USER_TRIGGERS
④低峰跑 python backfill_event_columns.py（998 万行 ≈ 15 min）
⑤--verify 校验 + 抽样 SQL 查物化列填充率
⑥功能验证 checklist（Lot / Alarm / 历史翻页 6 项）

风险 · 最坏情况

回填脚本与写入并发 → 部分行被覆盖？不会——ORM listener 和触发器幂等共存，payload_json 原文从未被修改。

回退方案

应用 git 回退旧版（旧版不引用新列），DBA 执行 DROP TRIGGER / INDEX / COLUMN 即可。payload_json 原文从未被修改。

部署口播：6 步都是常规操作，回填放低峰。最差情况是回填有偏差——没关系，新列是冗余提取字段，旧逻辑能兜住。
