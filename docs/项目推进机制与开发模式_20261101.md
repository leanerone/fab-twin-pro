# 项目推进机制与开发模式（深度思考）

> 回答两个问题：**这个项目怎么才能长期稳定地做下去？后面应该以什么模式开发？**
> 与《优化深度分析与行动计划_20261101》（做什么的清单）互补，本文讲**怎么运转**。
> 依据：项目的真实历史——哪些做法让它赚到了（三件套、缓存、契约测试），哪些让它痛过（人肉合并、双形态税、单点人）。

---

## 一、一个核心判断：稳定不取决于代码，取决于三件事

回顾项目 four 个月的起伏，代码好坏从来不是节奏失控的原因。真正决定"稳不稳"的是：

1. **主干是否永远绿** —— 任何时候拉 test3 出来都能跑、能演示。做到这一点，任何失误都只是"回退一个 PR"；做不到，每次开发都是在赌。
2. **边界是否清晰且被机器守护** —— 人改人的目录，公共改动有人把关。靠自觉的边界一定会退化（大家忙起来就抄近道），所以 CODEOWNERS + 分支保护必须是硬的。
3. **一切是否可重建** —— 硬件会坏（KIOXIA 已经坏过一次）、环境会丢、人会走。这个项目最可靠的安全网不是"小心别弄坏"，而是"15 分钟脚本重建 + 不可重建数据的定时备份"。

代码质量是这三件事的**结果**，不是原因。后续所有决策都从这三条铁律出发。

## 二、三条铁律（写进团队共识）

- **铁律 1 · 主干永远绿**：test3 任何时刻 `start-dev.bat` 一键起、六机台可看、smoke 14 项全过。合入前 CI 门禁是唯一放行条件，谁的红灯谁修。
- **铁律 2 · 边界即分工**：改自己目录自由；改别人的目录走 PR 由对方批准；改公共层（core/stores/api core/database）必须平台 review。边界清单就是《公共与模块边界定义》，不再口头约定。
- **铁律 3 · 一切可重建**：数据库 15 分钟脚本重建（已验证）；uploads/ 模型资产进 git；不可重建的数据（量产同步、AI 配置）每日备份任务。**把"可重建"当安全策略，而不是把"别弄坏"当策略。**

## 三、四种标准开发流（后面就这么开发）

项目里所有工作只有四种流，每种有固定的走法和"完成"的定义（DoD）。新任务来了先归类，不发明新流程。

### 流 1 · 功能开发（最常见）
```
看板认领 → feature/名字-内容 分支 → 只改自己目录 → CI 绿 → 自己合 → Sprint 演示
DoD：PR 模板自测证据填全 + 冒烟 14 项不红 + 演示时能讲清"用户看到了什么变化"
```

### 流 2 · 新机台接入（项目的王牌，成本已降到最低）
```
按《新机台建模SOP》：三件套（SVG + Motion JSON + deriver 文件两行 default 导出）
→ svg_kit validate 0 errors（CI 自动）→ inject_xxx_cycle.py 注入验证动画
→ sync_*_to_db.py 入库脚本进 PR
DoD：真机/参考图对照 + 22 步事件注入全链动画正确 + SOP 补充本轮发现的缺口
```
**这条流是项目的核心资产**：接一台新机台从"改代码"变成"交资产"。下一台机台（Endura 系）让钱鸣**不看代码纯按 SOP 走**——暴露的文档缺口当场补。SOP 能让人独立完成，才算真的稳。

### 流 3 · AI 功能开发
```
tests/ai/mock_providers 先行（替身 Dify/n8n/LLM）→ 实现 → 数据真实门禁
（答案 ≡ 直查 Oracle）→ 真实凭据联调（张亮）→ 才算完成
DoD：mock 链路测试过 + 真实联调过，两者缺一不可——mock 通过≠外部服务可用，
这是项目早期踩过的坑（写进交接文档的教训）
```

### 流 4 · 应急修复
```
总控（季世庆）开 [hotfix] PR → 最小修复 + 冒烟不红 → 当天合并 → 事后 24h 内补测试用例
DoD：修复附带一个"能证明这个 bug 存在过"的测试——同一坑不摔第二次
```

## 四、Sprint 机制：把愿景图切成垂直切片

最初的 Whimsical 分工图是**愿景**，不能直接当计划用——它按功能域竖着切（所有 EAP、所有 UI、所有 AI），导致每个 Sprint 都"什么都做了一点但连不起来"。稳定的做法是**横着切垂直切片**：

- ❌ "这个 Sprint 做 EAP 联机"（做完还是看不到东西）
- ✅ "这个 Sprint 让 **VPO 一台机台**的量产数据进来看板+动画+AI 查询"（端到端一条线打通，可演示）

**每个 Sprint 只背一个主目标**，从图上切一条竖线（一台机台 × 全链路，或一个页面 × 全功能）。2~3 周，以演示收尾（给老板/现场的人看），演示不过关的事项自动滚入下期并记录原因。

看板三列就够：`本Sprint / 进行中 / 完成`。禁止"进行中"超过 5 张卡——超过说明有人在并行开太多头。

## 五、架构演进原则：沿边界生长，用数据决定重构

**加东西永远沿边界加，不动内核：**
- 新机台 → 加资产文件（流 2）
- 新 AI 工具 → services/ai/tools.py 加一个注册函数 + 数据字典登记
- 新页面 → features/ 下新目录 + 一条路由
- 新表 → sql/ 版本脚本 + models.py（内核 review）

**什么时候才重构**：不看"代码美不美"，看 churn 数据——一个文件近 100 次提交里被改了 15+ 次、且每次都引发冲突或回归，才立项拆它（MachineDetail 当初就是这么被识别的：7/40 次提交）。没人反复碰的文件，再丑也不动。

**两个长线决策的判断框架**（已经分析过、等窗口的）：
1. **双形态税治理**：本地库迁 TIMESTAMP 的收益是删掉一批防御分支，但会动本地建表脚本。判断标准：等"消失一周演练"后团队自愈能力得到验证再做（改数据形态必然引入过渡期 bug）。
2. **监控选型**：Fluent Bit 方案已论证。判断标准：等影子运行（见下）开始后，没有监控就"看不见问题"时再上——需求出现时做，比提前做省一半。

## 六、量产上线策略：影子运行，单台试点，拒绝大爆炸

不要"某天切换到量产"。分三步：

1. **影子运行（2~4 周）**：一台机台（建议 VPO，李世庆的 Sprint Goal #1）的量产 EAP 数据只读接入——写进独立的表空间/schema，前端加"量产数据"开关。现场随便看，出任何问题零影响。这一步验证：数据形态假设、轮询性能、鉴权对接（7 个路由加了鉴权，外部集成会 403，必须在这步暴露）。
2. **单台正式**：影子期指标达标后，VPO 切正式写入。跑一个完整班次 + 一次告警风暴 + 一次网络抖动。
3. **横向铺开**：每接一台都是流 2 + 流 1 的重复，成本递减。铺开速度由"演示 + 稳定"双验收决定，不赶工期。

## 七、防线的系统视图（所有风险收拢成四道防线）

| 防线 | 守什么 | 现状 | 缺口 |
|---|---|---|---|
| 第一道 · 机器 | CI 门禁 + CODEOWNERS + smoke | 已建 | **分支保护还没开**（最紧迫的一件事）；E2E 进 CI（阶段C1） |
| 第二道 · 数据 | 可重建 + 备份 | runbook 已验证 | 备份定时任务；不可重建数据清单 |
| 第三道 · 人 | SOP + 演练 + 交接文档 | 文档齐 | "消失一周"演练没做；GitHub 独立账号还在共用 |
| 第四道 · 节奏 | Sprint 演示 + 看板 + 三条铁律 | 机制已写 | 恢复 Sprint Meeting（原图本来就有） |

其中**第一道防线的分支保护是当前唯一"零成本、高杠杆、还没做"的事**——GitHub Settings 里点几下，做完它，三条铁律才真正长在机器上。

## 九、机制里 AI 的角色

当前模式（洪佳琪指挥 + AI 执行）已跑通两轮大改造，把它写进机制而不是依赖默契：
- **机械性/跨目录的批量工作**（重构、迁移、文档生成、CI 配置）→ AI 主刀，人 review
- **需要现场判断的**（演示验收、需求取舍、对外沟通）→ 人主刀
- AI 产出一律走与人类相同的 PR + CI 门禁——机器产出不豁免机器门禁
- 每次大改造后由 AI 产出验收报告（本项目的既有实践），作为交接与审计材料

## 十、最后一句话

这个项目已经把"最难的两次转身"走完了：从单人开发到团队工程（第一次转身，本月初完成），下一步是从演示系统到生产系统（第二次转身，影子运行是入口）。**只要三条铁律不破、Sprint 不停、演示不断，项目就是稳的——剩下的都只是工作量。**
