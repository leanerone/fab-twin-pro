**目标**：消除 DT_EVENT_RAW 全表扫描，把 F5/F8 查询从 14s/43s 降到秒级以内。
**负责方**：DBA（索引）+ 后端（SQL 改写）｜ **跟踪项**：PROJECT_STATUS 遗留待办 #2

**步骤 A（DBA，生产库低峰执行）**：

```sql
-- 量产 Oracle，DBA 执行；ONLINE 避免锁表现行业务
CREATE INDEX IDX_DT_EVENT_RAW_TOOL_RECV
  ON DT_EVENT_RAW (TOOL_ID, RECEIVED_TS_UTC) ONLINE;

-- 执行后收集统计信息
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'DT_EVENT_RAW');
```

- 同时请 DBA 评估：热点 KPI 查询用 **Result Cache** 或**物化视图（MV）** 预聚合（Oracle 原生能力，零新组件）。
- 回退预案：`DROP INDEX IDX_DT_EVENT_RAW_TOOL_RECV;`

### T2　cachetools 进程内缓存（3 处）

**目标**：零部署成本先解决重复查询卡顿。**适用前提**：当前 FastAPI 是单进程 uvicorn，进程内缓存有效；未来多 worker 直接走 T7 Garnet。
**负责方**：后端

**步骤**：

```powershell
pip install cachetools
# requirements.txt 追加 cachetools
```

| 缓存点 | 位置 | TTL | 说明 |
|---|---|---|---|
| 机台状态推导 | [machines.py](../backend/routers/machines.py) `derive_machines_state()` | 60s | 每次请求 5 个 DT 大表查询 → 缓存 `{machine_id: {state, alarm_count_today, wafer_count_today}}` 整结果 |
| KPI 统计 | KPI 端点（现 `cache.py` 有 `set_kpi_stats` 壳未接线） | 60s | 直接用 TTLCache，不接 RedisCache |
| 模型配置 | `GET /api/models` | 300s | 现状每请求全表 + 逐行解析 CLOB；缓存后配置类低频变更可接受；**模型编辑器保存时需主动失效该 key** |

实现要点：
- 新建轻量封装（或直接在 `services/cache.py` 内加 `TTLCache` 实例与 `cached` 装饰器），键含查询参数哈希。
- **暂不接入 `RedisCache`**（cache.py 的 redis 直连无内存回退，连不上即报错；Garnet 就绪后 T7 再统一切换）。
- 日志打印 cache hit/miss，便于验收与调 TTL。

**验收标准**：
1. 主页 60s 内二次加载，机台列表接口耗时下降 ≥ 50%（对比后端日志耗时）。
2. 模型编辑器保存机型配置后，`GET /api/models` 返回的是新数据（失效逻辑生效）。
3. 后端重启无报错、无 Redis 连接异常（证明未依赖 RedisCache）。

**结论回填（2026-10-21）**：✅ 已完成并验收。cachetools 7.2.4 已入 requirements.txt；`services/cache.py` 新增 `LocalTTLCache`（线程安全 + hit/miss/invalidate 日志），三实例：`machine_state_ttl`(60s) / `kpi_stats_ttl`(60s) / `models_config_ttl`(300s)，分别接入 `derive_machines_state()`、`/api/machines/stats`、`GET /api/models`（create/update/delete/duplicate 四处写操作主动失效）。实测：`/api/machines` 625ms→8ms（↓98.7%，远超 ≥50%）；日志链 `MISS→HIT` 及保存后 `INVALIDATE ALL→MISS` 均正确；重启无 Redis 依赖报错。注意：API 测速脚本请直连 `127.0.0.1:8002`（本机 `localhost` 优先解析 `::1`，IPv4 回退产生 ~2s 假象，与代码无关）。

### T4　AI 聊天 SSE 透传改造（核心：解决一问一答）

**目标**：前端 ↔ FastAPI 透传代理 ↔ Dify Agent（SSE），实现打字机流式输出 + 工具调用过程可见 + 多轮上下文。
**负责方**：后端 + 前端 ｜ **依据**：AI 文档 §6.2 形态 A、§6.4「方向合适，接线方式要换」

**后端步骤**：
1. [ai_middleware.py](../backend/services/ai_middleware.py) 新增 `_stream_dify()` 生成器：直接向 Dify `chat-messages`（`response_mode: streaming`）发请求，逐行 yield SSE 原始事件。**不改动** `_consume_dify_stream()`（L1149）——旧聚合路径保留作回退。
2. [routers/ai.py](../backend/routers/ai.py) 新增 `POST /api/ai/chat/stream`，返回 `StreamingResponse(media_type="text/event-stream")`，从 `_stream_dify()` 透传事件；Dify Key 仍在后端读取（`ai_configs` 表），前端永不接触。
3. 透传事件类型：`agent_message`（正文分片）/ `agent_thought`（工具调用过程）/ `message_end`（usage 与结束）。token 统计逻辑改从透传流中截获 `message_end` 的 usage（不阻断透传）。
4. **IIS 反代必改**：`deploy/web.config` 的 API 反代规则需关闭响应缓冲（ARR `responseBufferLimit=0` / `flush` 即时下发），否则 SSE 会被攒成一次性返回——这是本任务最常见的翻车点。

**前端步骤**：
1. [AiAssistant.vue](../frontend/src/components/AiAssistant.vue) 与 [AIFloatingBall.vue](../frontend/src/components/AIFloatingBall.vue) 改调 `/api/ai/chat/stream`：用 `fetch` + `response.body.getReader()` 解析 SSE（**不能用 EventSource**，它不支持 POST/自定义头）。
2. UI：`agent_message` 追加渲染（打字机）；`agent_thought` 渲染为可折叠「工具调用过程」区；`message_end` 收尾。
3. 顺手统一两组件的 jump 契约**为对象传参**（AI 文档第五部分 #4：目前一个传对象、一个传裸时间戳）。
4. 旧端点 `/api/ai/chat` 保留一个版本周期，前端加开关可切回。

**验收标准**：
1. 机台详情页与悬浮球均为流式输出，首字时间明显早于旧版整段返回。
2. 连续两轮对话：第二轮能引用第一轮出现的机台/批次实体（多轮上下文生效）。
3. 工具调用过程在 UI 可见（agent_thought 折叠区有内容）。
4. 经 IIS 反代访问仍是流式（不是攒到最后一次性出来）。

**结论回填（2026-10-22 完成）**：

- **后端**：[ai_middleware.py](../backend/services/ai_middleware.py) 新增 `_stream_dify()`（逐事件透传 + `<FABTWIN>` 8 字符 lookahead 跨界拦截，块内结构化 JSON 不下发前端）与 `chat_stream()` 生成器（Dify 路由流式自管会话/usage 日志；非 Dify 路由委托 `chat()` 同步后包装单帧，前端一套渲染逻辑通吃）；`_parse_fab_block()` 解析 FABTWIN 块提取 table_data/jump/sources。旧 `_consume_dify_stream()`/`_call_dify()` 未动，保留作回退。[routers/ai.py](../backend/routers/ai.py) 新增 `POST /api/ai/chat/stream`（`StreamingResponse` + `X-Accel-Buffering: no`）。
