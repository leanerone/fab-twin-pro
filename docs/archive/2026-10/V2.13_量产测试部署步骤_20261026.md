## 一、核心问题先回答：要不要新增 DB 操作？

**要，共 4 项，全部幂等（可重复执行不报错）：**

| # | DB 操作 | 谁执行 | 方式 |
|---|---------|--------|------|
| 1 | `DT_EVENT_RAW` 加 3 列：`LOT_ID VARCHAR2(64)` / `EVENT_NAME VARCHAR2(128)` / `ALARM_CODE VARCHAR2(64)` | DBA（或后端自动） | sql/v2.13 脚本第 1 段；后端启动 init_db 也会自动补 |
| 2 | 建 3 个索引：`IDX_DT_EVENT_RAW_TOOL_RAW`（雷区B）/ `IDX_DT_EVENT_RAW_LOT` / `IDX_DT_EVENT_RAW_ALARM`（雷区A） | DBA（推荐） | sql/v2.13 脚本第 2 段；**量产 10M 大表建议 DBA 建**（见 §三 说明） |
| 3 | 建提取触发器 `TRG_DT_EVENT_RAW_EXTRACT` | **必须 DBA** | sql/v2.13 脚本第 3 段——兜底 WinForm 等直写 SQL、不经过后端 ORM 的写入路径 |
| 4 | 存量历史行回填三列 | 运维/DBA | 脚本 `tests/backfill_event_columns.py`，低峰跑 30~60 分钟 |

第 1/2 项虽然后端能自动做，但量产 10M 表上 `CREATE INDEX`（非 ONLINE）会阻塞 DML 数分钟，所以**量产标准做法是 DBA 先执行脚本，后端启动时全部跳过（幂等）**。标准版（XE/SE）无 ONLINE 选项，必须低峰窗口执行；Enterprise Edition 在 CREATE INDEX 末尾加 `ONLINE` 不锁表（脚本注释已给写法）。

## 三、部署顺序（重要，不要颠倒）

**为什么顺序重要**：新代码的 lot 查询是物化列等值过滤。若先发代码、后建列/回填，存量行三列为空 → 产测期间 Lot 追溯/产量统计查不到旧数据。

### 标准流程（在线、不停机）

| 步骤 | 操作 | 执行人 | 说明 |
|------|------|--------|------|
| 1 | 执行 `sql/v2.13_add_event_extract_columns.sql` 全脚本（1~4 段） | DBA | 加列 → 建索引 → 触发器 → 统计信息；此后**新写入**自动填列（ORM 走 listener、直写走触发器） |
| 2 | `git pull origin test3` | 运维 | 拉代码 |
| 3 | `pip install -r backend/requirements.txt`（如有变化）→ 启动后端 | 运维 | init_db 幂等：列/索引已存在则跳过，启动日志应无 ALTER 输出 |
| 4 | 跑回填脚本（低峰） | 运维/DBA | `python tests\backfill_event_columns.py`（在 tests 目录同级执行）；断点续跑，中断后重跑即可 |
| 5 | 校验回填 | 运维 | `python tests\backfill_event_columns.py --verify` |
| 6 | 功能验证 | 测试 | 见 §五 |

### 停机窗口模式（更稳，若允许 30~60 分钟只读）

停后端 → 步骤 1 → 步骤 4 → 步骤 2/3 → 步骤 5/6。

## 四、各步骤详细命令

### 步骤 1：DBA 脚本执行与验证

```sql
-- 执行 sql/v2.13_add_event_extract_columns.sql（SQL*Plus / SQL Developer / Navicat 均可）
-- 执行后验证（应返回 3 行列、3 行索引、1 行触发器）：
SELECT COLUMN_NAME, DATA_TYPE FROM USER_TAB_COLUMNS
 WHERE TABLE_NAME = 'DT_EVENT_RAW'
   AND COLUMN_NAME IN ('LOT_ID','EVENT_NAME','ALARM_CODE');

SELECT INDEX_NAME, STATUS FROM USER_INDEXES
 WHERE TABLE_NAME = 'DT_EVENT_RAW'
   AND INDEX_NAME IN ('IDX_DT_EVENT_RAW_TOOL_RAW','IDX_DT_EVENT_RAW_LOT','IDX_DT_EVENT_RAW_ALARM');

SELECT TRIGGER_NAME, STATUS FROM USER_TRIGGERS WHERE TRIGGER_NAME = 'TRG_DT_EVENT_RAW_EXTRACT';
```

### 步骤 4：回填脚本用法

```powershell
# 在仓库根目录执行；连接参数默认 fabtwin/fabtwin@localhost:1521/ORCLPDB，
# 与后端一致，可用环境变量覆盖：ORACLE_USER / ORACLE_PASSWORD / ORACLE_HOST / ORACLE_PORT / ORACLE_SERVICE
python tests\backfill_event_columns.py                  # 全量回填（10M 约 30~60 分钟，20K/批自动 commit）
python tests\backfill_event_columns.py --max-batches 50 # 分窗口执行：只跑 50 批（100 万行）后暂停
python tests\backfill_event_columns.py --verify         # 只校验不回填
```

- 进度文件：`tests/backfill_progress.txt`（`LAST=<raw_id>` 为断点，删除该文件则从头重跑）
- 每行无条件覆盖三列（幂等），重复执行无副作用
- 机器与 backend 同机部署时直接跑；异机部署把 5 个 ORACLE_* 环境变量指向量产库

### 步骤 5：回填校验

```sql
-- 总行数、有 lot 的行数、有告警码的行数（has_lot 应 > 0 且量级符合灌库比例）
SELECT COUNT(*) AS total, COUNT(LOT_ID) AS has_lot, COUNT(ALARM_CODE) AS has_alarm
FROM DT_EVENT_RAW;

-- 等值查询计时（应毫秒级，对比原 LIKE 645s）
SELECT * FROM (
  SELECT raw_id, tool_id, payload_json FROM dt_event_raw
  WHERE lot_id = 'LOT809570' ORDER BY raw_id DESC
) WHERE ROWNUM <= 10;
```

## 五、已知事项 / 注意

1. **ORA-01450 无害告警**：后端启动时若打印 `IDX_MACHINE_EVENTS_MID_TS ... ORA-01450 超出最大的关键字长度`，属预期——`machine_events/alarms/oht_positions/lots` 四张平台表的相关列是 `VARCHAR2(4000)`，复合索引键超 Oracle 6398 字节上限，init_db 捕获并跳过。历史上因 test31 参数顺序 bug 这些索引从未真正尝试创建，本轮修正后才出现该日志。消除需 DBA 缩列宽（另立任务，不阻塞本版）。
2. **FABTWIN_TOKEN_SECRET 生产必设**（test31 安全改动：HMAC token 7 天过期依赖该密钥）。
3. 触发器与后端 listener 幂等共存：都只在列为 NULL 时填充，互不覆盖。
4. 回填脚本固定 20K/批 commit，undo 占用可控；**不要**手动改大批量（10M 一次性 UPDATE 会产生数 GB undo）。
5. 11g 兼容已验证：回填 SELECT 用 `ROWNUM` 子查询写法；触发器 `REGEXP_SUBSTR` 对 CLOB 可用（11gR1+）。
6. 触发器正则按 `"lot_id": "值"` 带引号字符串匹配，JSON null 不匹配 → 保持 NULL；`"NULL"` 字符串脏数据归一为 NULL，与后端 `_norm` 一致。

## 六、回退方案

| 对象 | 回退方式 |
|------|----------|
| 代码 | `git checkout <上一版tag/commit>` 重启后端即可（旧代码本就读 payload_json LIKE，行为回到原样） |
| 触发器 | `DROP TRIGGER TRG_DT_EVENT_RAW_EXTRACT;` |
| 索引 | `DROP INDEX IDX_DT_EVENT_RAW_LOT;` 等 3 个（见 sql 脚本末尾） |
| 新增列 | `ALTER TABLE DT_EVENT_RAW DROP (LOT_ID, EVENT_NAME, ALARM_CODE);`（列一删回填数据随之消失） |
| 回填本身 | 无需单独回退 |
