# 功能模块化方案：按功能切文件夹，一个功能一个负责人（2026-11-03）

> 接续《模块化分工与自治合并_会议材料》。那份解决“怎么合并不找人”，这份解决“文件夹到底怎么切”。
> **核心转变：从「按技术位置分」改为「按功能分」——每个功能模块前后端垂直自包含、只有一个负责人。**

---

## 一、先说结论：为什么现在还是“交叉”

代码核查（ver3 实际扫描）：

| 检查项 | 结果 |
|---|---|
| features 业务组件之间跨域 import | **0 处** |
| 后端 routers 之间相互 import | **0 处**（只引公共 auth） |
| 数据域 router 之间 | **0 处互引** |

**代码其实已经解耦了，乱的是“目录归属规则”。** 现有 `features/` 是按**技术层**切的（motion 动画 / machines 面板 / ai 助手 / dashboard 看板 / editor 编辑器），
于是一个完整功能被摊到 4~5 个文件夹。以「看一台机台」为例：

```
views/MachineDetail.vue              ← 页面壳（无人认领的过渡区）
features/motion/MachineMotion2D.vue  ← 钱鸣（动画引擎）
features/machines/PlaybackBar.vue    ← 季世庆（回放）
features/machines/LotList.vue        ← 季世庆（批次）
features/ai/AiAssistant.vue          ← 朱明钊（AI）
backend: history/events/lots/alarms/oxe/oht/recipes 七个 router ← 同一功能的数据
```

改一个“机台详情”要跨 5 个前端目录 + 7 个后端文件、2~3 个人。这就是“交叉”的根源。

另两处人为交叉：机台详情/看板文档写成“朱明钊界面 + 季世庆数据”**共管**；views 下 6 个页面壳归属未定义。

---

## 二、划分原则（先定规则，再分文件，最后才分工）

1. **按用户能看到的「功能」切，不按代码技术层切**。判定一句话：*“这部分东西删了，哪个功能会从用户眼前消失？”*
2. **一个功能模块 = 一个文件夹 = 一个负责人**。前后端、页面、资产都在里面。**禁止共管模块**；必须两人协作的，按规则 3 拆。
3. **多人会碰的功能，沿「生产者/消费者」重新划开**：引擎/资产归生产者模块，页面归消费功能模块，通过公开组件接口引用，不进对方目录。
4. **依赖只能单向朝下**：功能模块 → 平台内核，模块之间不直接 import 对方内部文件。
5. **公共内核只放“被 ≥2 个功能用、且改坏会全体挂”的东西**，越小越好。

---

## 三、切成 6 个功能模块 + 1 个内核

| 模块（建议名） | 它是哪个“功能” | 负责人 | 前端目录 | 后端目录 |
|---|---|---|---|---|
| **① 模型库** | 建机台模型、调动画、管素材 | **钱鸣** | `modules/model-library/` | `backend/modules/model_library/` |
| **② 生产监控** | 看机台实时/回放、看板、告警、批次、天车、配方 | **季世庆** | `modules/production-monitor/` | `backend/modules/production_monitor/` |
| **③ AI 助手** | 问数、对话、AI 配置、语音 | **朱明钊** | `modules/ai-assistant/` | `backend/modules/ai_assistant/` |
| **④ 系统管理** | 登录、用户、权限 | **洪佳琪**（过渡） | `modules/system-admin/` | `backend/modules/system_admin/` |
| **⑤ 智能体集成** | Dify/n8n 部署与对接资产（零平台代码） | **张亮** | —（资产/脚本） | `deploy/`、`docs/integration/` |
| **⑥ 平台内核** | 公共底座、CI、E2E 门禁 | **洪佳琪** | `shell/` + `core/` | `backend/core/`、main/config/db |

> 关键变化：
> - **“看机台”整个功能（页面+回放+面板+7 个数据 router+db_poller）收进 ②生产监控，季世庆一人负责**；动画引擎是 ① 生产出来、② 直接用的组件。
> - 看板/FloorPlan 从朱明钊划给季世庆——它消费的是实时数据，归“生产监控”才闭环。朱明钊从此只专心 AI。
> - 登录/用户从“过渡”正式立为模块④，不再是真空。

### 3.1 每个模块里装什么（以「②生产监控」为样板）

```
modules/production-monitor/
├── pages/MachineDetailPage.vue     # 机台详情页（唯一入口）
├── components/PlaybackBar.vue      # 回放条
├── components/HistoryReplay.vue
├── components/LotList.vue  AlarmList.vue
├── components/DashboardPage.vue    # 看板页（含 FloorPlan）
├── components/floor/ FloorPlan.vue FloorView3D.vue KpiCards.vue MachineList.vue
├── components/machine/MachineModel3D.vue MachineVpo3DView.vue
├── api/  (history/events/lots/alarms/oht/oxe/recipes 的前端调用)
└── README.md  （模块说明/公开接口）

backend/modules/production_monitor/
├── routers/ history.py events.py lots.py alarms.py oht.py oxe.py recipes.py rvmessages.py debug.py machines.py floors.py
├── services/ db_poller.py simulator.py ods.py html_parser 不用放
└── README.md
```

### 3.2 ①模型库 与 ②生产监控 的边界（最容易吵的一处，先定死）

- **① 钱鸣拥有**：所有 `models/` 资产、动画引擎（MachineMotion2D、useMotionPlayback、derivers、useExprEval）、模型编辑器、上传/入库。
- **② 季世庆拥有**：机台详情**页面**，他 `import` ① 暴露的 `<MachineMotion2D>` 组件。
- 规则：① 保证组件的 props/事件接口稳定（写在模块 README 的“公开接口”里）；**② 不准进 ① 的目录改引擎**，引擎需求提给 ①。
- 这与现在 App 装配关系一致（组件零互引），**只是把页面归到消费方**，改动小。

### 3.3 平台内核（⑥）——刻意保持小

| 层 | 内核文件 | 为什么在内核 |
|---|---|---|
| 后端 | main.py 装配点、config、database、models(ORM 总表)、schemas 基类 | 应用入口/连接/表结构 |
| 后端 | core/（events_query、deps）、services/{security,cache,realtime,perf,time_utils} | ≥2 模块共用的底座 |
| 前端 | shell/（main.js、App.vue、router 装配表、AppHeader）、api/core.js（request/token）、stores/{app,auth} | 全局骨架/数据流 |
| 工程 | requirements、package.json、vite、.github/、CI | 改了影响所有人 |

> 内核不是“谁都可以放杂物的筐”。新东西先问“是不是 ≥2 个功能都要、改坏全挂”，不是就进功能模块。

## 四、一个功能从“文件夹”到“工作标准”的定义（这才是分工标准）

每个模块 README 必须写清四件事，这就是该负责人的工作边界：

1. **公开接口**：对外暴露的页面路由、组件名、API 前缀、事件/数据结构（别人只准碰这些）
2. **内部文件**：别人不可 import 的目录
3. **独立可验**：怎么证明这个功能没坏（模块自测命令 + 对应 CI job）
4. **数据归属**：它写/读哪些表（建表改表走内核 review）

有了这四条，“工作标准”不再是“你大概负责 AI”，而是“你负责 modules/ai-assistant 目录及其公开契约”。

## 五、迁移怎么走（不做大爆炸，保持主干绿）

五个小批次，每批 = 纯搬家 + import 路径修正，**路由 URL、API 前缀、表名一律不变**，每批 CI 全绿才合：

| 批次 | 动作 | 风险 |
|---|---|---|
| M1 | 建 `modules/` 目录与 README 骨架；迁 **③AI 助手**（后端 services/ai 已是包，最干净，先试路径） | 低 |
| M2 | 迁 **①模型库**（models/ 不动位置，前端 motion+editor+views/ModelEditor+ModelManagement 收编，后端 models/uploads router） | 中 |
| M3 | 迁 **②生产监控**（最大：MachineDetail 页+面板+7 router+db_poller+Dashboard/FloorPlan） | 中高，单独一 PR 充分回归 |
| M4 | 立 **④系统管理**（Login/UserManagement/auth/users）、归位 **⑤集成资产** | 低 |
| M5 | 内核收口到 shell/+core/；CODEOWNERS 改按新模块；CI 加“模块越界 import”静态检查 | 低 |

**收益不是“目录变好看”**，是 M5 那条静态检查：CI 直接禁止 `modules/A` import `modules/B` 的内部文件，边界从此由机器守，不靠开会强调。

## 六、需要你拍板的 6 件事

1. **看板/FloorPlan 从朱明钊划给季世庆**，是否同意？（数据闭环在季世庆；不同意则看板要单立模块）
2. **机台详情页归消费方季世庆**，钱鸣只拥有动画引擎组件——两人是否接受这个生产者/消费者边界？
3. **MachineManagement（机台 CRUD）归谁**：它是“主数据管理”，建议归①模型库（钱鸣，因为模型绑定在这页）或④系统管理；倾向①。
4. **登录/用户模块④负责人**：洪佳琪过渡后交谁？朱明钊还是季世庆？
5. **models.py ORM 总表**留内核（建表走 review）还是允许各模块持有自己的表文件由内核聚合？建议先留内核、表按模块分注释段。
6. **模块中文名**是否采用：模型库 / 生产监控 / AI 助手 / 系统管理 / 智能体集成？

## 七、切完之后的协作形态（对照你的原始诉求）

- “不同功能文件夹独立” → `modules/` 下 4 个有代码的功能模块，各自前后端垂直完整
- “以功能分工” → CODEOWNERS 一个目录一个人，不再有共管
- “多人修改的功能重新划分” → 引擎（钱鸣）与页面（季世庆）沿生产者/消费者拆开，靠公开组件接口连接
- “改完上传我就能用” → 模块内 CI 绿自合；跨模块只有公开接口，接口不变就不会连带别人
- “随时合并随时拆分” → 模块是自包含单元：新功能加目录、下线功能删目录，内核不动
