### 0.3 AI 架构现状（用户未来目标对齐度评估）

| 维度 | 现状 | 对齐「Dify/n8n为主、本地仅基础处理」目标 | 差距 |
|------|------|----------------------------------------|------|
| 统一AI入口 | ✅ 全部走 /api/ai/chat → AIMiddleware.chat() | 100% | 无 |
| 规范化响应 | ✅ _normalize_response + sources/tool_calls/jump_timestamp 结构化 | 100% | 无 |
| 本地 fallback | ✅ _local_rule_engine 9个工具直查DB + 关键词命中n8n | 100%（离线可用兜底） | 无 |
| RAG引用 | ✅ retriever_resources / docs 双兼容解析 | 98% | 需真实Dify环境验证TC06~TC07 |
| n8n 双调用链路 | ⚠️ A链路（UI直接→n8n）✅；B链路（Dify内部→n8n工具）需在Dify端配置HTTP节点 | 70% | B链路工具对接需要Dify里接n8n凭据 |
| Dify 多 App 路由 | ❌ 仅 1 个 dify_app_id | 40% | 悬浮球/机台详情/质量工程师等多入口需按scope路由 |
| 响应处理器 | ❌ 单文本渲染，无注册表 | 20% | CSV下载/工单卡片/图表等特殊类型回答显示为纯文本 |
| n8n workflow 元数据 | ❌ 5个路径硬编码 | 50% | 新增自动化需改代码发版 → 应改为DB注册表 |
| Dify 变量透传 | ❌ machine_id+user_role 硬编码 | 60% | 业务专用Dify App 需要产品ID/工单号/日期范围 |
| 凭据安全 | ❌ 明文存 ai_configs | 30% | 多系统凭据需 AES-GCM 加密统一管理 |
| 编排流水线 | ❌ 无pipeline | 0% | 多Dify+n8n串联需单步处理（非Dify内部流程） |
