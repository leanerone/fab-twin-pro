## 一、现状问题清单（9大混乱根源）

### 1. HTML 原型遗留（死代码 8000+ 行）

| 文件 | 行数 | 状态 | 说明 |
|------|------|------|------|
| `frontend/public/OXE_2D.html` | 2,816 | **死文件** | 早期原型，Vue 组件已完全独立实现 |
| `frontend/public/VPO2D.html` | 1,139 | **死文件** | 同上 |
| `frontend/public/VPO_3D.html` | 3,980 | **死文件** | 同上 |
| `scripts/extract_vpo_model.py` | 52 | **死文件** | 从 HTML 提取 JSON 的过渡脚本 |

这些文件占 8,000+ 行，**没有任何代码引用它们**，但一直留在项目里，误导新人以为这是参考实现。

### 2. 两套并行但互不兼容的架构

```
架构A（PODOPENER）                架构B（OXE）
─────────────                    ────────────
MachineVpoView.vue               MachineModel2D.vue
  → 程序化 SVG（draw2DBase）       → SVG 硬编码在 template
MachineVpo3DView.vue             MachineModel3D.vue
  → JSON 拼 box/cylinder           → Three.js 程序化建模
useAnimationConfig.js            无动画配置
  → DB优先/文件fallback            → 直接操作 runState
```

两套架构的 props 不统一、动画驱动方式不同、配置来源不同，**新增机型时不知道该抄哪套**。

### 3. 组件职责过重（万能组件）

以 MachineVpo3DView.vue 为例，一个组件同时做：
1. Three.js 场景初始化（相机/灯光/地面/控制器）
2. 模型加载（fetch JSON → buildMachineFromJson）
3. 动画驱动（事件→phase→translate/rotate/scale/flash...）
4. 实时渲染（requestAnimationFrame 循环）

**代码量 > 1,200 行**，任何改动都可能影响其他功能。

### 4. 配置散落在 4 个地方

同一套 PODOPENER 动画配置，分散在：
- DB `machine_model_configs.animation_config_json`（运行时优先）
- `frontend/src/configs/machine-animations/podopener.json`（fallback）
- `frontend/public/models/podopener-2200-3d.json`（3D 模型部件定义）
- `frontend/public/VPO_3D.html`（死文件，但残留了 fallbackModel 数据）

**改动画要同时检查 3 个地方**，不知道哪个生效。

### 5. 事件驱动方式不一致（至少 3 种）

| 组件 | 驱动方式 | 事件来源 |
|------|----------|----------|
| MachineVpoView/Vpo3DView | `useAnimationConfig` phase key 映射 | `props.events` 数组 |
| MachineModel3D | `runState` 对象直接驱动 | `props.runState` 对象 |
| MachineModel2D | `runState` 对象直接驱动 | `props.runState` 对象 |
| FloorPlan | 自定义事件处理 | `props.events` 数组 |
| LineView3D | WebSocket 实时事件 | 独立 EventSource |

同一个 VFEI 事件（如 `POD_PLACED`），在不同组件里有完全不同的处理链路。

### 6. view_mode 枚举混乱

数据库里的值：
```
vpo, vpo3d, vpo-3d, threejs, hybrid, isometric, iso, svg-vpo
```

MachineDetail.vue 里用硬编码字符串匹配：
```js
const isVpo = cfg.view_mode === 'vpo' || cfg.view_mode === 'vpo3d' || 
              cfg.view_mode === 'vpo-3d' || ...
```

**没有枚举定义**，新增一个 view_mode 要改 N 个地方的字符串判断。

### 7. 命名空间三分裂

同一个 POD 外壳，有三个不同的名字：

| 场景 | 名字 | 位置 |
|------|------|------|
| 2D SVG | `pod2dLayer` / `podShell` | SVG 的 id |
| 3D JSON | `podShellGroup` | Three.js Group 的 name |
| animation target | `podShell` | animation_config 的 target key |

靠 `targets.podShell.view_2d` 和 `targets.podShell.view_3d` 做映射，**任何一方的命名变动都会导致动画失效**。

### 8. 缺乏抽象层（每个组件从零造轮子）

```
MachineVpoView      自己实现：SVG绘制 + 动画 + 事件处理
MachineVpo3DView    自己实现：Three.js场景 + JSON加载 + 动画 + 事件
MachineModel2D      自己实现：SVG硬编码 + 动画 + runState处理
MachineModel3D      自己实现：Three.js场景 + 程序化建模 + 动画 + runState
MachineIsoView      自己实现：等轴测投影 + ...
```

**没有统一的 ModelLoader、MachineRenderer、AnimationDriver 接口**，每个组件重复实现 Three.js 场景初始化、动画插值、事件解析。

### 9. 死代码/空目录堆积

```
frontend/public/models/README.md          → 描述不存在的 GLB 目录
frontend/public/models/machines/.gitkeep  → 空目录
frontend/public/models/vehicles/.gitkeep  → 空目录
scripts/extract_vpo_model.py              → 过渡脚本
frontend/public/OXE_2D.html               → 原型
frontend/public/VPO2D.html                → 原型
frontend/public/VPO_3D.html               → 原型
```

## 二、规范化目标

1. **一套架构**：所有机型走统一的加载-渲染-动画链路
2. **文件驱动**：2D 交付 SVG，3D 交付 GLB，动画在网站上配置
3. **配置统一**：所有动画配置只存在一个地方（DB `animation_config_json`）
4. **接口统一**：统一的 props 接口、统一的事件驱动方式
5. **枚举定义**：view_mode 用 TypeScript 枚举或常量对象
6. **命名统一**：2D id / 3D name / animation target 三合一
7. **抽象分层**：ModelLoader → MachineRenderer → AnimationDriver
8. **清理死代码**：删除所有不再引用的文件

## 三、规范化架构设计

### 3.1 分层架构

```
┌─────────────────────────────────────────────────────┐
│  MachineDetail.vue（壳，负责选择 2D/3D 渲染器）        │
├─────────────────────────────────────────────────────┤
│  MachineRenderer2D.vue    │  MachineRenderer3D.vue   │
│  （统一2D渲染接口）         │  （统一3D渲染接口）        │
├─────────────────────────────────────────────────────┤
│  SvgLoader               │  GltfLoader / JsonLoader  │
│  （加载 SVG 文件）         │  （加载 GLB/JSON 文件）     │
├─────────────────────────────────────────────────────┤
│  animationStore（Pinia Store，统一动画配置和驱动）      │
├─────────────────────────────────────────────────────┤
│  DB: machine_model_configs.animation_config_json     │
└─────────────────────────────────────────────────────┘
```

### 3.2 核心抽象

#### 3.2.1 ModelLoader（模型加载器）

职责：根据 `views_config` 加载模型文件，返回渲染器需要的对象。

```typescript
interface ModelLoader {
  // 加载 2D 模型
  load2D(config: View2DConfig): Promise<SVGSVGElement>
  
  // 加载 3D 模型
  load3D(config: View3DConfig): Promise<THREE.Group>
}

// 实现类
class SvgLoader implements ModelLoader {
  async load2D(config) {
    if (config.svg_source === 'procedural') {
      return createProceduralSVG(config)  // 兼容旧机型
    }
    const res = await fetch(config.svg_source)
    const text = await res.text()
    return parseSVG(text)
  }
}

class GltfLoader implements ModelLoader {
  async load3D(config) {
    if (config.model_source.endsWith('.glb')) {
      return loadGLB(config.model_source)
    }
    if (config.model_source.endsWith('.json')) {
      return loadJSONModel(config.model_source)  // 兼容旧机型
    }
  }
}
```

#### 3.2.2 MachineRenderer（渲染器接口）

```typescript
interface MachineRenderer {
  // 初始化（创建场景/插入DOM）
  init(container: HTMLElement, modelConfig: ModelConfig): Promise<void>
  
  // 执行动画
  executeAnimation(anim: AnimationConfig): void
  
  // 重置到初始状态
  reset(): void
  
  // 销毁（清理资源）
  dispose(): void
  
  // 选中部件（用于动画编辑器）
  selectPart(partId: string): void
  
  // 获取部件列表
  getParts(): PartInfo[]
}
```

#### 3.2.3 AnimationDriver（动画驱动器）

```typescript
// 统一的事件处理流程
function onEvent(eventCode: string) {
  // 1. 查找 phase
  const phase = animationStore.findPhase(eventCode)
  if (!phase) return
  
  // 2. 查找动画配置
  const anims = animationStore.findAnimations(phase.key)
  
  // 3. 执行动画
  for (const anim of anims) {
    renderer.executeAnimation(anim)
  }
}
```

### 3.3 数据流规范化

```
VFEI 事件流
    │
    ▼
[EventProcessor] 解析 event_code
    │
    ▼
[animationStore] 查找 phase → animation
    │
    ├─→ 2D: MachineRenderer2D.executeAnimation(anim)
    │         → SvgAnimator.translate('podShell', {from, to, duration})
    │
    └─→ 3D: MachineRenderer3D.executeAnimation(anim)
              → ThreeAnimator.translate('podShellGroup', {from, to, duration})
```

**关键改变**：
- 事件处理从组件内部移到 animationStore
- 组件只负责渲染和动画执行，不负责事件解析
- 同一个事件，2D 和 3D 的动画配置从同一个 `animation_config_json` 读取

### 3.4 view_mode 枚举定义

```typescript
// frontend/src/constants/viewModes.ts
export const ViewMode = {
  SVG_2D: 'svg-2d',           // 纯2D SVG
  SVG_3D: 'svg-3d',           // 纯3D SVG（等轴测）
  HYBRID: 'hybrid',           // 2D + 3D 切换
  GLB_3D: 'glb-3d',           // GLB 3D
  PROCEDURAL_3D: 'proc-3d',   // 程序化3D（兼容旧OXE）
  PROCEDURAL_2D: 'proc-2d',   // 程序化2D（兼容旧PODOPENER）
} as const

export type ViewModeType = typeof ViewMode[keyof typeof ViewMode]

// MachineDetail.vue 中使用
import { ViewMode } from '@/constants/viewModes'

const is2D = [ViewMode.SVG_2D, ViewMode.PROCEDURAL_2D].includes(cfg.view_mode)
const is3D = [ViewMode.GLB_3D, ViewMode.PROCEDURAL_3D].includes(cfg.view_mode)
```

**旧值映射**（迁移时兼容）：
```
vpo        → ViewMode.PROCEDURAL_2D
vpo3d      → ViewMode.PROCEDURAL_3D
vpo-3d     → ViewMode.PROCEDURAL_3D
threejs    → ViewMode.PROCEDURAL_3D
hybrid     → ViewMode.HYBRID
isometric  → ViewMode.SVG_3D
iso        → ViewMode.SVG_3D
svg-vpo    → ViewMode.SVG_2D
```

### 3.5 命名统一方案

**原则**：一个部件只有一个名字，2D/3D/animation 通过约定后缀区分。

| 部件 | 统一 base name | 2D SVG id | 3D GLB name | animation target |
|------|---------------|-----------|-------------|------------------|
| POD外壳 | `podShell` | `podShell` | `podShell`（Group） | `podShell` |
| 锁扣 | `latch` | `latch` | `latch`（Group） | `latch` |
| 花篮 | `cassette` | `cassette` | `cassette`（Group） | `cassette` |
| 扫描线 | `scanLine` | `scanLine` | `scanLine`（Group） | `scanLine` |
| 信号灯 | `signal` | `signal` | `signal`（Group） | `signal` |

**实现**：
- 2D SVG：`id="podShell"`
- 3D GLB：Object name = `podShell`（代码查找时自动加 Group 后缀）
- animation target：`"target": "podShell"`（代码根据 2D/3D 自动映射到正确的 id/name）

### 3.6 配置来源统一

**目标**：动画配置只存在一个地方。

```
┌─────────────────────────────────────────┐
│  运行时优先：DB.animation_config_json    │ ← 唯一权威来源
├─────────────────────────────────────────┤
│  开发 fallback：静态 JSON 文件           │ ← 仅开发时/首次部署用
│  (frontend/src/configs/machine-animations/)
├─────────────────────────────────────────┤
│  编辑入口：网站动画编辑器                  │ ← 修改后写回 DB
└─────────────────────────────────────────┘
```

**删除**：不再从 `VPO_3D.html` fallbackModel 读取（HTML 文件删除）。

| 风险 | 影响 | 应对 |

## 九、关键决策点

在你确认开始修改前，需要确认以下 3 点：

1. **是否接受删除旧组件**（MachineVpoView/Vpo3DView/Model2D/Model3D/IsoView）？
   - 优点：代码量减少 60%+，维护简单
   - 风险：替换期间可能有短暂不稳定

2. **view_mode 枚举是否接受重命名**？
   - 数据库里的旧值（vpo/vpo3d/threejs 等）需要迁移脚本
