## 三、性能实测（1000 万行）

### 3.1 正常路径：索引 + TTL 缓存表现良好

| 路径 | 冷态 | 暖态（缓存命中） |
|---|---|---|
| `/api/machines`（57 台 × 当日聚合） | 0.047s | 0.017s |
| `/api/history/{tool}` 同日 limit=500 | 1.23s | **0.039s** |
| `/api/history/{tool}/timeline`（拉 5000 行 Python 聚合） | 1.55s | —（120s TTL） |

test31 的历史回放缓存治理在千万级上有效。

### 3.2 🔴 雷区 A：CLOB LIKE 全表扫（交接文档"雷区 1"的千万级实证）

`/api/lots/{id}` 与 `/api/lots/{id}/events` 对 `payload_json LIKE '%lot%'` 过滤
（`backend/routers/lots.py:206`、`:245`；全仓共 14 处同类查询）：

| 场景 | 实测耗时 |
|---|---|
| lot 命中 | **645.2s（10 分 45 秒）** |
| lot 不存在 → 404 | **702.8s（11 分 43 秒）** |
| /events（LIKE + limit 5000） | **568.3s（9 分 28 秒）** |

未命中也要扫完全部 1000 万个 CLOB 才能回 404。AI 聊天"查批次"必触发该路径，量产不可用。
**方案**：物化 `lot_id/alarm_code/event_name` 普通列 + 索引（`init_db()` 幂等加列/建索引机制现成：
`database.py:193-262`），历史回填脚本 + DBA 触发器填新数据，14 处 LIKE 改等值过滤。预计分钟级 → 毫秒级。

### 3.3 🔴 雷区 B（本次新发现）：缺 `(tool_id, raw_id)` 复合索引，实时/详情导航近全表扫

现象：写+回读用例耗时 406s，事件详情 21s。逐步计时拆解（全新 tool_id，插入 1 行后）：

| 查询 | 实测 |
|---|---|
| 实时模式 `/history?limit=N`（`tool_id IN(...) ORDER BY raw_id DESC`） | **490.9s** |
| 事件详情"上一条"（`tool_id IN(...) AND raw_id < :x ORDER BY raw_id DESC`） | **457.8s** |
| 事件详情"下一条"（反方向 ASC） | 0.18s |

**根因**：排序键是 raw_id，但只有 `(tool_id)` 单列索引，没有 `(tool_id, raw_id)`。
优化器要么取该机台全部行（~17 万）再排序，要么沿 PK(raw_id) 顺序扫、逐行回表比对 tool_id；
当目标机台在 raw_id 序上稀疏/靠后（**新接入机台、当天无数据机台、查看老事件的 prev**），
接近扫完整张千万级表。带日期的历史回放走 `(tool_id, received_ts_utc)` 所以是秒级，平时被掩盖。

代码位置：实时查询 `routers/history.py:429-433`（分支 C）；详情 prev/next `routers/history.py:668-685`；
同类模式还有 `services/db_proxy/main.py`、`routers/rvmessages.py:113` 的 rv/history。

**方案**：一条 DDL（可走现有幂等建索引机制下发；大库首次创建约 1-2 分钟）：

```sql
CREATE INDEX IDX_DT_EVENT_RAW_TOOL_RAW ON DT_EVENT_RAW (TOOL_ID, RAW_ID);
```

## 四、正确性 / 数据一致性问题

### #3 keyset 翻页第二页与第一页完全重叠（新发现，已 xfail 钉住）

`backend/routers/history.py:41-57` `_decrement_raw_id`：零填充数字后缀减 1 后丢失宽度——

```
'SEED0009489888' → int(9489888)-1 = 9489887 → 'SEED9489887'
```

`SEED9489887` 字符串序**大于**所有 `SEED000...`，`WHERE raw_id < :cursor` 命中全部行，
前端"加载更多/下一页"永远重复第一页。已离线验证修复（纯数字 raw_id 即量产 NUMBER 形态不受影响，
所以此前未暴露）：

```python
return f"{prefix}{int(num_str) - 1:0{len(num_str)}d}"
```

### #4 RV 写入：同秒主键碰撞 → 500 丢事件

`backend/routers/rvmessages.py:44` `raw_id = f"TID.{int(datetime.now().timestamp())}"` 秒级精度，
同一机台同秒两条消息第二条 PK 冲突 500、事件丢失（测试实测复现）。
`routers/debug.py:74` 的毫秒+随机数写法正确，应对齐。PK 为全表唯一，跨机台也会撞。

### #5 非法 payload：先 commit 后解析，500 但数据已落库

`rvmessages.py:67-69`：先 `db.commit()` 双表写入，之后才 `json.loads(data.payload_json)`；
非法 JSON 时客户端收到 500，行却已提交——响应与数据不一致。应在写库前校验/宽容解析。

### #6（环境/健壮性）AI 会话表缺失时 import 报错

每次启动可见 `[AI] 会话映射清理跳过: ORA-00942`——AI 四张表不随 `init_db()` 自动建
（需手工 `sql/create_ai_tables.sql`），而 `ai_middleware` import 即实例化并访问 DB。
不影响本次读写测试，但新机器部署必踩。

## 五、结论与建议顺序

读路径整体（索引+缓存）在千万级可用；**写入链路与实时导航存在两个分钟~十分钟级雷区**，
均为"代码/索引可解、不需要改架构"：

1. 【一行修复，立即可做】#3 `_decrement_raw_id` 保宽度；#4 raw_id 毫秒+随机；#5 payload 校验前置。
2. 【一条索引】雷区 B：`(tool_id, raw_id)` 复合索引，本地可立即 A/B 验证（490s → 预期毫秒级）。
3. 【需 DBA 窗口】雷区 A：lot_id/alarm_code/event_name 物化列 + 回填 + 触发器，14 处 LIKE 改写。
4. 【部署文档】AI 四张表初始化纳入 runbook 或 init_db。

本报告与测试套件均为新增提交，不包含任何产品代码改动；上述修复等确认后分批进行。
