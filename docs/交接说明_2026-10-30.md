### 2.3 挖出的三个真问题（**重点，别再踩回去**）

1. **AI 返回的 `sql` 是假的** —— `ai_tools.py` 里多处 `"sql": "SELECT ..."` 是**硬编码字面量，
   从未执行过**。你以为看到了查询依据，其实是样板文字。
   现改为：真实执行的语句上浮，装饰性语句标注「参考查询（本次由 ORM 取数，并未执行此语句）」。
2. **ORM 与物理库严重漂移** —— `models.Machine` 声明 `type`/`status`，真实 `MACHINES` 表是
   `PROCESS_TYPE`/`STATE`。按 ORM 生成的字典会让 AI 写出必然 ORA-00904 的 SQL。
   字典反射源已改为物理数据字典。
   > 由此还发现：`machines` 表实际带 `TEMP/PRESSURE/GAS_FLOW/RF_POWER`，
   > 而旧工具答复用户「系统不含传感器数据」是**错的**。
3. **`table_data` 类型不符 → `/api/ai/chat` 一直 500** —— 这是 AI 链路始终没跑通的最后一因
   （`AITableData` 要求单对象 `{headers, rows:[[...]]}`）。

## 3. 任务二：模型域 —— 部分完成

### 3.1 先理解机制（SVG / Motion / deriver 三者关系）

如果你没接触过这块，记住这条链：

```
SVG（静态图，部件带 id）
   ↓  事件进来
Motion JSON（事件名 → 动画编排，ext.deriver 指定推导器）
   ↓
deriver（前端 JS，把事件 payload 推导成动画参数）
   ↓
前端动起来
```

- **资产成对存放**：`models/user/<机型>.svg` + `<机型>.motion.json`
  （现有：`oxe-drm-topview.*`、`podopener-2200.*`、`amat_metsput.*`）
- **接线表**：`machine_model_configs`，动画配置写在 `animation_config_json` 字段（Text，存 JSON 字符串）
- **deriver 位置**：`frontend/src/motionDerivers/`（**在前端，不在后端**）
- **绑定方式**：Motion JSON 的 `ext.deriver` 填名字 → 前端 `motionDerivers/index.js`
  的 `factories` 里注册同名工厂函数，前端无需改其他代码

### 3.2 LAM2300 已完成的部分

照 `docs/assets/machine-references/LAM2300.jpg` 布局建模：
ATM 大气端（3×Load Port + Aligner + 2×Buffer + Control Rack + ATM 机器人）
→ 2×Airlock → 中央圆形 VTM（含机器人）→ 4×PM 放射。

### 3.3 剩下两步（照着做即可，约 1.5 小时）

**第 1 步：写 deriver `frontend/src/motionDerivers/lam2300.js`**

契约照抄 `oxe.js`（同目录，是最佳模板）：导出一个工厂函数，返回
`{ derive(step, payload), commit(step, params), reset() }`：

- `derive(step, payload)`：把事件 payload 推导成动画参数，返回 `{ ok, params, info }`
- `commit(step, params)`：提交记忆（如 lastPort）
- `reset()`：清空内部状态

注意：OXE 的槽位面板是 `mapping` 逐槽字符（`when` 白名单不允许 `[]`，下标必须在 deriver 展开），
LAM2300 若有同类需求照此处理。
